## Executive verdict

Paseo is a good reuse base for the **host boundary**: a Node daemon owns provider processes, a WebSocket client model serves mobile/desktop/CLI, timeline and directory replicas recover from cursors, and the optional relay is endpoint-encrypted. The architecture is explicitly local-first (`docs/architecture.md:1-40`), and agent state plus native provider history have separate durability contracts (`docs/architecture.md:334-349`). That matches Caret's requirement that the Mac keeps working when the UI closes and an iPhone resumes the same session.

Paseo's OMP provider is **not a complete OMP harness**. OMP 18.1.18 defines 42 `RpcCommand` variants (`/tmp/omp-source.nmo5hX/packages/coding-agent/src/modes/rpc/rpc-types.ts:28-93`), while Paseo's `OmpRpcCommandSchema` accepts 16 (`/tmp/caret-paseo-src.CNT1Jx/packages/server/src/server/agent/providers/omp/rpc-types.ts:499-547`). Paseo's runtime adds raw fire-and-forget `steer` and `follow_up` sends (`cli-runtime.ts:258-267`) and performs generic protocol negotiation (`protocol-session.ts:21-35`), but those do not provide the OMP command response/ID semantics. These are schema counts, not a product-support percentage: negotiation has a shared transport path, and raw sends have different response semantics. Use the per-surface gaps below rather than treating schema membership as verified behavior.

There is no `rpc-ui` launch mismatch at the pinned floor. OMP 18.1.18 documents `rpc-ui` (`docs/cli-reference.md:193-201`); its `main.ts:1844` marks the session as UI-capable and `main.ts:2058-2062` passes `setToolUIContext` only for `rpc-ui`. Paseo launches `--mode rpc-ui` (`providers/omp/agent.ts:2233-2248`, `runtime.ts:122-147`), which is the right mode for approval dialogs. However, OMP deliberately sets `PI_NO_PTY=1` for `rpc-ui` (`main.ts:1545-1547`), so the OMP RPC session has no interactive PTY. A separate Paseo/Code-OSS terminal can satisfy a user terminal surface, but it is not the same as OMP's in-process PTY semantics.

The architecture decision should therefore keep one OMP execution owner in the Caret host, retain the Code-OSS Mac workbench, and reuse Paseo's client/relay/session patterns. Before calling the result “all OMP core”, extend the adapter or add a version-pinned, fully tested bridge for the missing command/event surfaces below. Do not silently substitute a common-denominator session API.

## Compatibility and licensing gates

1. **Keep the pinned runtime.** `rpc-ui` is present in OMP 18.1.18, so no OMP upgrade is needed to remove a launch mismatch. Paseo's generic floor is only `16.3.9` (`providers/omp/provider-config.ts:9-15`), which is too broad to assert the full 18.1.18 command/event contract.
2. **Add a full-harness compatibility gate.** At startup, record the exact `omp --version` output and protocol-ready frame. For a “full OMP core” profile, require the pinned 18.1.18-compatible feature set (or probe each command and fail closed per feature). A v2-ready frame alone proves framing, not command support. Keep a legacy profile only when the UI visibly marks unsupported controls.
3. **Extend one adapter boundary.** Grow `OmpRuntimeSession` and its schemas from `runtime.ts:45-80` / `rpc-types.ts:499-547` to cover all commands and event side channels in the pinned OMP source. Use OMP's own `rpc-client.ts` behavior as the semantic reference for immediate acknowledgements, serial-vs-background dispatch, pages/cursors, cancellation, and stale-session errors.
4. **Bridge host URIs and UI as typed protocols.** Add `set_host_uri_schemes` plus read/write/cancel/result handling, and preserve extension UI option metadata, timeouts, cancel/status/widget/title/editor-text, and `extension_error`. Keep permission identity bound to tool, effective arguments, request ID, process incarnation and policy version.
5. **Keep durable delivery in the Caret host.** Paseo's `JsonlRpcProcess` IDs are process-local. Caret's host envelope must journal `deviceId`, `commandId`, `sessionId`, incarnation, payload hash and result status; same ID/same payload joins the old result, a different payload is rejected, and an effect without a terminal receipt becomes `outcome_unknown` rather than an automatic retry.
6. **Do not claim MCP injection or PTY from the existing adapter.** `supportsMcpServers:false` is an explicit contract. OMP-native MCP config can remain available inside the child, while caller-scoped MCP requires a deliberate trusted extension/bridge. `rpc-ui` disables OMP PTY; provide a separate host terminal for P10 and test it independently.
7. **License provenance.** OMP has MIT in `LICENSE` and `packages/coding-agent/package.json:11-12`; `gh repo view can1357/oh-my-pi --json licenseInfo` reports MIT. Paseo's `LICENSE` grants Apache-2.0 to Paseo except third-party components; `gh repo view getpaseo/paseo --json licenseInfo` reports GitHub's unclassified `Other`, so preserve the local LICENSE/NOTICE and audit transitive dependencies before copying modules. Neither license grants use of product trademarks or hosted service capacity.

## Recommended implementation surface for Caret

- Reuse Paseo's daemon/client/relay/session persistence and timeline cursor patterns behind the Caret host. Keep one OMP process/session owner; do not run a second Paseo supervisor against the same native session.
- Retain Caret's Code-OSS Mac workbench for buffers, LSP/debug/test/editor state. Use a host protocol to connect it to the same OMP session and workspace/artifact receipts.
- Treat the current Paseo OMP files as a starting adapter, not the product contract. The first G1 slice should add command/event inventory tests for OMP 18.1.18 before broad UI work.
- Validate E1 (web), E3 (limiter/native), and E4 (reconnect/idempotency) only after the full OMP bridge, host PTY boundary, MCP decision, browser/artifact paths and permissions have explicit receipts.

## Integrated review corrections

- Schema membership is not measured feature coverage; protocol negotiation and raw steer/follow-up exist outside the 16-command schema. Full command IDs are in [source inventory](evidence/omp-rpc-2026-09-12/source-inventory.json).
- E2EE does not prove approved-device identity. Paseo SECURITY.md describes ephemeral phone keys and lacks live-session replay protection. Caret device allowlist/revoke and durable idempotency remain implementation gates; see [relay assessment](CARET-RELAY-ASSESSMENT-2026-09-12.th.md).
- A separate user PTY does not close the OMP PTY semantics gap imposed by rpc-ui; G1 needs an explicit bridge/patch/SDK decision.
- All Supported labels above mean source paths identified, not tests run in Caret. Paseo adapter suites were not run.
